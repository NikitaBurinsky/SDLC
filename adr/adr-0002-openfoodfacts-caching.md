# ADR-0002: Стратегия двухуровневого кэширования данных Open Food Facts API

## Контекст и постановка задачи

Система «NutriTrack» должна предоставлять пользователю возможность мгновенного поиска продуктов по штрихкоду и текстовому наименованию на основе глобальной открытой базы данных Open Food Facts (OFF). 

Однако прямой прокси-запрос на каждый ввод символа в строке поиска («typeahead search») несет в себе критические риски:
1. Внешний публичный API Open Food Facts имеет жесткие ограничения по частоте запросов (rate limits) и периодически испытывает повышенное время задержки (latency > 500–1200 мс).
2. При сбоях в сети или падении серверов Open Food Facts пользователи NutriTrack не должны терять возможность выбирать ранее добавленные продукты и вести журнал питания.
3. По условиям нефункциональных требований (SYS-NFR-PERF), время отклика API для 95% запросов должно быть менее 200 мс.

Какую архитектурную стратегию кэширования и репликации применить для обеспечения высокой отзывчивости и отказоустойчивости?

## Драйверы решения

* **SYS-NFR-PERF**: Время отклика API < 200 мс для типовых операций;
* **SYS-NFR-REL**: Устойчивость к сетевым сбоям внешнего сервиса (Graceful Degradation);
* **Защита от rate-limits**: Не превышать лимиты Open Food Facts API (максимум несколько сотен запросов в минуту от одного IP);
* **Экономия ресурсов базы данных**: Снижение нагрузки на дисковую подсистему PostgreSQL.

## Рассмотренные варианты

1. **Прямой прокси-запрос без кэширования (Direct Pass-Through)**: каждый клиентский запрос немедленно перенаправляется в Open Food Facts API.
2. **Только оперативное кэширование в оперативной памяти бэкенда (L1 In-Memory Cache / MemoryCache)** с TTL = 1 час.
3. **Полная предзагрузка всего дампа базы Open Food Facts в PostgreSQL** (офлайн-дамп объемом > 50 Гб).
4. **Гибридное двухуровневое кэширование (L1 MemoryCache + L2 PostgreSQL Persistent Cache)** с асинхронным fallback-механизмом.

## Итог решения

Выбран вариант **№4: Гибридное двухуровневое кэширование (L1 MemoryCache + L2 PostgreSQL)**.

### Механика работы:
1. **L1 (In-Memory)**: Горячие поисковые строки и часто запрашиваемые штрихкоды сохраняются в памяти процесса Kestrel с использованием `IMemoryCache` со скользящим сроком жизни (Sliding TTL) 30 минут. Время отдачи — менее 5 мс.
2. **L2 (PostgreSQL `FoodItems`)**: При промахе в L1 поиск выполняется по локальной таблице `FoodItems`. Если продукт ранее хотя бы единожды искался любым пользователем, он уже сохранен в локальной базе с атрибутом `is_cached_from_off = true`. Время отдачи — менее 25 мс.
3. **L3 (Внешний REST API OFF)**: Только при полном отсутствии совпадений в L1 и L2 бэкенд выполняет асинхронный HTTP-запрос к `world.openfoodfacts.org`. Полученные продукты атомарно сохраняются в таблицу `FoodItems` и прогревают кэш L1.
4. **Fault Tolerance (Circuit Breaker)**: Если сервис OFF недоступен (таймаут 1.5 с или HTTP 5xx), система возвращает пользователю локальные частичные совпадения из L2 с предупреждающим мета-флагом, не прерывая работу приложения ошибкой 500.

### Последствия

* **Хорошо**:
  * 90%+ поисковых запросов закрываются внутри инфраструктуры NutriTrack со скоростью < 30 мс;
  * Система полностью защищена от блокировок по IP со стороны Open Food Facts;
  * Локальная база со временем органически накапливает наиболее востребованные продукты целевого региона пользователей;
  * При отключении интернета или недоступности внешнего API пользователи продолжают полноценно пользоваться каталогом.
* **Плохо**:
  * Данные о составе продуктов могут отставать от актуальных правок в Open Food Facts (решается фоновой задачей обновления устаревших записей старше 30 дней);
  * Увеличение объема занимаемого дискового пространства в PostgreSQL (некритично для сотен тысяч записей, ~100 Мб).
* **Нейтрально**:
  * Требуется поддержка составных индексов `trgm` (триграммный индекс) в PostgreSQL для быстрого нечеткого текстового поиска по названию.

## Подтверждение

1. Нагрузочный интеграционный тест, эмулирующий 50 одновременных запросов с замером 95-го перцентиля времени отклика.
2. Тест изоляции сети (Mock HTTP-клиента с симуляцией `HttpRequestException`) — проверка корректной отдачи локального кэша L2 без выбрасывания необработанных исключений.
